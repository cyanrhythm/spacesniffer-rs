## 3. 总体评价

这是一次**高质量的迁移**：不是把 egui 代码逐行翻译成 GPUI，而是按 GPUI 的 retained 模型重新组织了状态与视图，并把原 README 里记录的几处老问题一并解决。

### 3.1 亮点

1. **分层清晰**：`app.rs` 只管状态、导航、命中、删除；`views/` 四个模块各管一块 UI；`scanner`/`treemap`/`colors` 与框架解耦。比原来 806 行单文件混渲染好维护。
2. **canvas 自绘是正确选择**：`prepaint` 里算布局 + `shape_line`，`paint` 里只提交 quad（`views/treemap_view.rs:89-105, 317-330`）。几千个格子不会变成几千个 element，性能路径清晰。
3. **导航按绝对路径恢复**（`app.rs:377-411`）：真正修掉了「子项按大小重排 → `nav_stack` 索引漂移」的老问题，并且扫描期间能保持当前钻入层级。
4. **扫描器安全性增强**：不跟随符号链接、Unix `(dev, ino)` 祖先链检测目录环、`MAX_DEPTH` 兜底，并补了对应单测（`scanner.rs:35-58, 231-243, 288-303`）。
5. **交互体验升级**：原生右键菜单自动贴边、删除确认对话框、删除失败通知、空目录点空白返回、悬停信息卡、跟随系统深浅色、CLI 直接扫描路径、`prompt_for_paths` 原生目录框（不再依赖 `rfd`）。
6. **工程配套到位**：13 个单测、README 重写、API 速查文档、两张截图、`app_id` 设置（Wayland 图标）、多语言 key 更新。

### 4.1 P0 — 删除操作仍然按数组下标定位，有删错目标的风险

**位置**

- `app.rs:59` `context_target: Option<Vec<usize>>`
- `app.rs:62` `delete_target: Option<Vec<usize>>`
- `app.rs:416-420` 菜单删除时按 `target` 解析条目
- `app.rs:464` 确认框 OK 时再次按 `target` 解析条目
- `app.rs:630` `self.context_target = Some(target)`

**机理**

右键时把「当前导航栈 + 子项下标」存为 `Vec<usize>`。真正的删除发生在用户点确认之后，此时再次用这组下标去 `get_entry_by_path()` 解析——但扫描线程每 250ms 会用新快照替换整棵树，子项还会按大小重新排序（`scanner.rs:344, 361-367`），数组下标会整体漂移。

**触发路径**

1. 扫描进行中（UI 每 100ms 拉取一次进度，`app.rs:211-233`）
2. 右键目录 A，选择「删除」
3. 确认对话框打开期间，新的 partial 快照到达并重排 children
4. 点确认 → 按旧下标解析到目录 B → **删除 B**

即使没有扫描，只要树在对话框打开期间发生任何重排，同样会命中错误条目。

**影响**

数据安全级别：可能误删用户文件/目录。`delete_target` 字段只写不读（`app.rs:421, 446, 452`），也说明这条链路没有闭环。

**修复建议**

菜单/确认框改存绝对路径，而不是下标：

```rust
// 右键时
let entry_path = entry.path.clone();
let is_dir = entry.is_dir;

// 确认时
let Some(entry) = self.find_entry_by_path(&entry_path) else {
    // 条目已不存在：通知并放弃
    return;
};
if entry.path != entry_path {
    // 理论不可达；作为防御
    return;
}
```

要点：

- `find_entry_by_path` 在树中按 `PathBuf` 查找，或先按下标解析再校验 `path` 一致。
- 校验失败时给用户明确反馈（已有 Notification 能力）。
- 删除同时清理只写不读的 `delete_target` / `context_target`。

**验收标准**

- 扫描中右键 A、等待快照重排、确认删除 → 要么删 A，要么拒绝并提示；绝不删 B。
- 为「树被替换后删除」补一个可复现的单测（可把树变换抽成纯函数）。

### 4.2 P1-1 — CJK 字体族名拼错，且 `Font::fallbacks` 在当前 GPUI 快照中疑似未被消费

**位置**

- `src/fonts.rs:35`

```rust
return Some(("YaHei Monaco Hybrid", Cow::Borrowed(EMBEDDED_FONT)));
```

- `src/views/treemap_view.rs:348-355` 用它构造 `FontFallbacks`

**证据**

字体内部族名与代码不一致（`fc-scan` 实测）：

```
family=YaHei Monaco Hybird
fullname=YaHei Monaco Hybird
postscript=YaHeiMonacoHybird
```

字体作者把 `Hybrid` 拼成了 `Hybird`，代码里写的是正确拼写，`FontFallbacks` 按名字查找会落空。

更关键的是：在 `gpui-pre 0.3.9` 源码里 grep `Font::fallbacks`，只找到赋值处（`style.rs:547/565`、`styled.rs:734`），**没有找到 shaping 路径上的消费点**；文本实际依赖 cosmic-text 的系统 fallback。也就是说这段「显式 CJK 回退族」大概率没有生效，README 第 21 行的描述偏乐观。

**影响**

- Windows/macOS 有系统 CJK 字体，问题不可见（截图均为 Windows）。
- 在最小化 Linux 环境（没有 Noto CJK 等）中，画布里的中文标签、空目录提示可能显示豆腐块。
- 重量级的内嵌字体（22MB）可能没有参与实际排版，等于白背体积。

**修复建议**

1. 先把族名改成真实值 `"YaHei Monaco Hybird"`。
2. 在**无系统 CJK 字体**的环境实测一次：treemap 中文文件名、`(空目录)` 提示。
3. 如果仍不生效，二选一：
   - 把 `cx.theme().font_family` 设为内嵌字体族（UI 与画布统一）；
   - 或确认 `add_fonts` 后 cosmic-text 的自动 fallback 能命中，再删掉无效的 `FontFallbacks` 代码并修正 README。
4. 若确认 `Font::fallbacks` 不生效，README 不应声称「显式声明 CJK 回退族」。

**验收标准**

- 在只安装拉丁字体的环境启动，画布中文正常显示。
- 若做不到，README 明确写出「依赖系统 CJK 字体」。
